# v0.2.0: decline, releases, settings diff, UI certificates

Four changes, shipped as one release (v0.2.0) so the five nodes are
reinstalled once. One branch, one commit series per part, one PR merged on green.

## Decisions already made (user, 2026-10-12)

| Topic | Decision |
|---|---|
| Settings diff source | Diff the current vs target binary's `cockroach gen settings-list` |
| UI cert trust | Private "Rollout UI CA" with X.509 name constraints, trusted once on the Mac |
| Renewal | Agent subcommand plus a systemd timer on the cluster |
| Key review | Fingerprint shown plus an authenticated download; the key is never rendered in a page |
| CA key home | One node only for now; renewal runs only there. Later: password-encrypted CA key in the DB, re-keyed on each renewal (todo.d) |
| Deploy authority | User authorized reinstalling all five nodes and restarting agents and CockroachDB as needed (2026-10-12) |

## Part 1: Decline a proposal, show why restart is blocked

**Problem.** With a `proposed` rollout open, the UI offers only Approve.
Cancel only appears for active or failed rollouts. The restart button is
hidden without a reason, and after a CLI cancel the leader re-proposes the
same target on its next tick.

- New rollout status `declined`. It is terminal, like `cancelled`, and is
  not counted as open.
- UI action **Decline** appears on a `proposed` rollout. The form carries
  the rollout id, and the POST refuses if the open rollout's id differs.
  Event: `rollout_declined`.
- CLI: `decline [--reason]` declines the open proposal. `undecline
  <version>` deletes the decline so the version can be proposed again.
- `propose_next_rollout` skips any target that has a `declined` row. It
  records `proposal_skipped` with "25.4.17 → 26.1.8 was declined" at most
  once per target, not every tick.
  - A newer patch on the same line is a new target and is proposed
    normally. For example, if 26.1.8 is declined, 26.1.9 can still be
    proposed.
- When a rollout is open, `available_actions` shows the restart as
  `RestartBlocked` with the reason, instead of omitting it.

## Part 2: Release catalog and Releases panel

**Problem.** Release discovery crawls `/tags` up to 10 pages (976 tags
today; the 10-page cap silently drops lines past 1000) on every
proposal attempt. Unauthenticated GitHub allows 60 calls/hour per IP.

- **Discovery** switches to `GET /repos/cockroachdb/cockroach/git/matching-refs/tags/v`.
  It returns every `v*` tag (645 today) in one unpaginated response. The
  existing stable-version filter still applies.
- **Cache.** New table `release_catalog`, a single row with
  `versions_json`, `fetched_at`, `last_error` and `refresh_requested_at`.
  - The leader refreshes it when the cached copy is more than 1 hour old,
    or when a refresh was requested and the last fetch is more than
    10 minutes old.
  - A failed fetch keeps the old list and records `last_error`.
  - **Proposals read the cache,** never GitHub directly. Release-notes
    fetches happen only when a proposal is actually published.
- **Panel "Releases"**, shown below Rollouts:
  - one row per release line, from the cluster's current line upward, with
    the newest patch and a link to its release notes;
  - the cluster's own line, the open proposal, and each later step of the
    upgrade path are marked;
  - a footer reads "checked N min ago", plus `last_error` if the last
    fetch failed.
- **"Check now"** button (session and CSRF required) sets
  `refresh_requested_at`.
- `build_upgrade_steps` is unchanged. The panel calls it with the cached
  versions, so the path the UI shows is the path the leader will take.

## Part 3: Settings diff on proposals

**Overrides** are read with `SELECT variable, value, setting_type, default_value
FROM [SHOW ALL CLUSTER SETTINGS] WHERE origin = 'override' AND variable <> 'version'`.
This needs only the role's existing `MODIFYCLUSTERSETTING`. `system.settings`
would need a new SELECT grant, and it has no default column.

**Defaults** come from running `cockroach gen settings-list --all-settings
--format=ndjson` on both the installed binary and the target binary. The
leader runs both at proposal time, after the artifact download that
proposals already do. The target binary is extracted into a scratch dir
under the versions dir and deleted afterwards. The plan's first task
verifies that this dir allows exec inside the unit's sandbox.

**Findings** are stored on the rollout row as `settings_report_json`:

- **Warnings** (our overrides):
  - removed in the target (missing even with `--all-settings`);
  - default changes between current and target;
  - type changes.
- **Info:** every non-overridden setting whose default changes. It's shown
  collapsed, count first.

**Approval.** Warnings join the release-note warnings on the Approve card.
The existing "I reviewed the warnings" checkbox covers both, and the
checkbox is required when either list is non-empty.

**Redaction.** Values are shown only for `b`, `i`, `f`, `d`, `e` (bool,
int, float, duration, enum) settings. Strings and byte sizes print
`(redacted)`, and the names `cluster.secret`, `enterprise.license` and
`cloudstorage.http.custom_ca` are always redacted. Values never go into
`events` or the audit log; only names do.

**Failure.** If either binary can't be run, the proposal is still
published. It carries `settings_report_json = {"error": "..."}`, and the
card shows "settings diff unavailable: …" as a warning that must be ticked
off.

## Part 4: UI certificates (private CA, staged rotation)

### Trust

- **`ui-cert init-ca`** creates "Rollout UI CA" (ECDSA P-256, 10 years).
  It is run once, as the cockroach user, on a node chosen by the operator.
  - **Name constraints** (critical): one permitted `dNSName` subtree per
    host and one `iPAddress` /32 per node IP. Nothing else is permitted.
  - **Hosts** default to the agents' short hostnames and the gossip IPs,
    with `--extra-name` for more. For today's cluster that is
    unimatrixzero, unimatrixone, len-serv-001, len-serv-002 and
    len-serv-003, plus the five IPs.
  - **Output:** `ui-ca.crt` and `ui-ca.key` in
    `/var/lib/cockroach-rollout-agent/ui-ca/` (dir 0700, key 0600, owned
    by cockroach).
- The CA key **never** goes in the database. Renewal can only run on
  nodes that hold it.
- **Adding a host later** requires a new CA, which the operator trusts
  again on the Mac. The constraints are fixed when the CA is created.
- **Verify the name constraint.** Before the docs claim the constraint
  holds, test it on the Mac: a leaf signed by the CA for a name outside
  the set must be rejected by Safari and Chrome.

### Leaf certificates

- ECDSA P-256, valid 397 days. SANs are every host and IP in the CA's
  constraint set. EKU is serverAuth.
- **New table `ui_certs`:**
  - `fingerprint` (SHA-256 of the DER) is the primary key;
  - `cert_pem`, `key_pem`, `chain_pem`;
  - `status`: `staged` | `approved` | `retired` | `rejected`;
  - `not_before`, `not_after`, `created_by`, `created_at`, `decided_by`,
    `decided_at`.
- **Trade-off, stated plainly:** the leaf key is readable by anyone who
  can SELECT from the coordination schema, which today means the
  `rollout` client cert. A holder of that cert can impersonate the UI to
  a browser on the LAN. That role can already approve upgrades, so it adds
  no new authority. The CA key, which could mint new certs, is not in the
  database.

### Staging

Three ways to stage a cert. All of them only stage; nothing goes live
without a human approval.

- `ui-cert renew [--before 30d]`
  - It acts only if this node holds the CA key and the approved cert
    expires within `--before`, or none exists.
  - It takes the `ui_cert_renew` lease so two key-holders can't both
    stage.
  - It generates a leaf and stages it, logging the `ui_cert_staged` event.
- **systemd timer** `cockroach-rollout-agent-ui-cert.timer`, installed by
  the installer. It runs daily, with jitter, and calls `ui-cert renew`.
- **Upload:** a UI form takes a PEM cert and key. It is session- and
  CSRF-protected and logs the `ui_cert_uploaded` event. On upload it
  validates:
  - the key matches the cert;
  - the chain verifies to the UI CA (`ui_certs` row `chain_pem`, or the
    CA cert on disk);
  - the cert has not expired.

  The CLI `ui-cert stage <cert> <key>` runs the same validation.

### Review and approval (UI)

- A "UI certificate" panel shows:
  - the active cert (fingerprint, SANs, validity, issuer);
  - any staged cert, with the same details plus a diff of SANs against the
    active cert;
  - per agent, which fingerprint it is serving.
- **Downloads** need a session. `GET /ui-cert/<fingerprint>/cert.pem` and
  `/key.pem` send `Cache-Control: no-store` and
  `Content-Disposition: attachment`. Every key download writes a
  `ui_cert_key_downloaded` event (actor plus fingerprint; never the key).
- **Approve** and **Reject** POSTs carry the fingerprint and refuse if it
  is not the staged one. Approving sets it to `approved` and retires the
  previous cert (the event is `ui_cert_approved`). The CLI equivalents are
  `ui-cert approve <fp>` and `ui-cert reject <fp>`.

### Distribution (every agent)

**When it runs.** On every tick, if the approved fingerprint differs from
the one it serves, the agent follows these steps:
1. Checks that the cert chains to the UI CA, that its own IP and hostname
   are in the SANs, and that it has not expired.
2. Writes `node.crt` and `node.key` atomically to
   `/var/lib/cockroach-rollout-agent/ui-certs/`, keeping the old pair as
   `*.prev`.
3. Hot-reloads through axum-server's `RustlsConfig::reload_from_config`.
   There is no process restart, so a mid-rollout agent is not bounced.

**On failure.** If any check fails, the agent keeps serving the old cert
and records the error in its agent row.

**Heartbeat.** It reports `ui_cert_fingerprint`, a new `agent_status`
column, so the panel shows distribution progress.

**Cert dir resolution** (amended during the final review):
1. An explicit `CROACH_ROLLOUT_UI_CERTS_DIR` wins.
2. Otherwise the installed pair in
   `/var/lib/cockroach-rollout-agent/ui-certs/` is used, but only if it
   loads. A broken pair is skipped rather than disabling the UI.
3. Otherwise the CockroachDB certs dir is used.

The agent never writes into the CockroachDB certs dir.

### Dependencies

- `rcgen` moves to `[dependencies]` with `default-features = false,
  features = ["ring", "pem", "x509-parser"]`. The aws-lc-rs count must
  stay 0.
- `x509-parser` (already pulled in by rcgen's feature) parses SANs and
  validity.

## Rollout of v0.2.0 itself

1. **Ship.** Merge the four PRs, then cut v0.2.0.
2. **Remote nodes.** Reinstall the four remote nodes with the existing
   loop, which the user authorized on 2026-10-12. The installer gains the
   timer unit.
3. **unimatrixzero.** The user reinstalls it locally.
4. **Bootstrap the CA** (user, on one node):
   1. `ui-cert init-ca`, then `ui-cert renew`, which stages the first leaf.
   2. Download `ui-ca.crt` and trust it on the Mac.
   3. Approve the leaf in the UI after checking its fingerprint and SANs.
   4. Optionally remove the Cockroach CA trust added on 2026-10-12.
5. **Not covered by this release's authorization:** approving 26.1.8,
   starting a rolling restart, and approving any UI cert. Each needs the
   user's explicit go-ahead.

## Out of scope

- Binding the existing Cancel and Finalize actions to a rollout id
  (deferred minor from v0.1.0). Decline is bound from the start.
- Automatic re-trust on the Mac.
- Rotating the CA itself.
